# Nebula 文档结构设计说明

> 状态：生效中
> 最近更新：2026-07-24
> 定位：说明 `docs/` 文件夹的分层架构、各层职责与文档归属规则。本目录同时作为**产品文档的依据**与**开发实现的依据**。新文档必须按本说明归类。

## 1. 设计目标

- **双依据定位**：既是产品设计的依据，也是开发实现的依据——每份文档必须明确服务哪类受众、交付什么
- **可扩展**：新文档有明确归属，不会散落在根目录
- **分层清晰**：产品视角与技术视角分离，规格与规范分离
- **可执行**：specs 层文档可直接对照实现，conventions 层文档可直接对照编码
- **生命周期管理**：区分长期文档（产品/架构/规范）与临时文档（计划/分析）
- **可发现性**：每层有 README 索引，根 README 是总入口

## 2. 七层分类架构

```
docs/
├── README.md                  总索引（入口）
├── _structure.md              本文件（结构设计说明）
│
├── product/                   产品文档（做什么）
├── architecture/              架构文档（怎么设计 + 怎么开发）
├── specs/                     功能规格（实现契约，开发照着做）
├── conventions/               规范文档（编码/接口/测试约定，开发必读）
├── decisions/                 架构决策记录 ADR（为什么这么决策）
├── analysis/                  分析文档（现状如何）
└── plans/                     执行计划（怎么落地）
```

## 3. 各层职责与交付物

### 3.1 `product/` — 产品文档

**回答**：做什么？为谁做？功能边界是什么？

**内容**：
- 产品定位与目标
- 功能矩阵（feature matrix）
- 用户画像（user personas）
- 产品路线图（roadmap）
- 竞品对比
- 术语表（glossary）

**归属判断**：文档描述"产品应该有什么功能"或"产品方向" → 放这里。

**受众**：产品经理、设计师、开发、利益相关方。

**对开发的价值**：开发理解"为什么做这个功能"的依据，是 specs 的上游输入。

### 3.2 `architecture/` — 架构文档

**回答**：系统怎么设计的？模块如何划分？数据如何流动？**如何新增一个模块/组件/接口？**

**内容分两类**：

**架构设计**（描述系统结构）：
- 系统总览（monorepo 结构、技术栈、包依赖关系、数据流）
- 模块架构（如大屏设计器架构、蓝图运行时架构）
- 数据模型设计（跨模块的共享数据模型）
- 部署架构

**开发指南**（描述如何动手，step-by-step）：
- 新增大屏组件指南（注册表 / renderer / 属性 schema / 图标）
- 新增后端模块指南（module / controller / service / prisma / 权限）
- 新增 API 端点指南（endpoints.ts / http.ts / TanStack Query hook）
- 新增菜单/路由指南（navigation.ts / routes 文件）
- 环境配置与本地调试指南
- 数据库迁移指南（Prisma multi-schema）

**归属判断**：
- 文档描述"系统的整体设计结构与原理" → 放这里
- 文档是"某个功能的详细规格" → 放 `specs/`
- 文档是"step-by-step 的开发操作手册" → 放这里（开发指南子类）

**受众**：开发、架构师。

**对开发的价值**：开发理解全局架构、知道如何动手新增功能的依据。**新人入职必读**。

### 3.3 `specs/` — 功能规格

**回答**：某个功能的具体规格是什么？**前后端契约是什么？开发照着什么实现？**

**内容**（每个功能一个子目录，含以下交付物）：
- 功能概述与目标
- **数据模型 / Schema 定义**（Zod schema、Prisma model、TypeScript 类型）
- **API 契约**（端点、请求/响应结构、错误码、鉴权）
- **UI/UX 规格**（页面布局、交互流程、组件结构）
- 状态管理与数据流
- 测试策略（单元/集成/E2E 覆盖点）
- 实现检查清单（checklist，开发自验）

**归属判断**：文档是"某个功能的完整设计包，开发可直接对照实现" → 放这里。

**组织方式**：`specs/<feature-name>/` 下放该功能的多个文档，含 `README.md` 索引。

**对开发的价值**：**开发实现的核心依据**。开发拿到 spec 应能独立完成实现，无需反复确认细节。spec 必须包含可直接落地的契约（Schema、API、类型），而非仅概念描述。

**与 architecture 的区别**：architecture 是"整体怎么设计"，specs 是"这个功能具体怎么实现"。

### 3.4 `conventions/` — 规范文档

**回答**：写代码/API/测试/文档时遵循什么约定？**开发必读，编码前先看这里。**

**内容**：
- 编码规范（TypeScript/React/NestJS 约定，从 `.trae/rules/project_rules.md` 沉淀）
- API 设计规范（命名、响应格式、错误码、BizCode 段位分配）
- Schema 规范（Zod 使用约定、discriminatedUnion 模式、判别联合扩展约定）
- UI/UX 规范（shadcn/ui 使用边界、canvas 渲染 vs 编辑器外壳的组件选型）
- 测试规范（何时写测试、覆盖率要求、测试命名、mock 约定）
- 提交规范（Conventional Commits、分支命名）
- 文档编写规范（格式、元信息、命名）

**归属判断**：文档是"所有开发者都要遵守的约定" → 放这里。

**对开发的价值**：**编码前的必读规范**，保证代码一致性。与 `.trae/rules/project_rules.md` 的关系：`project_rules.md` 是 AI 专用规则（机器读），本目录是人类协作者规范（人读），两者内容对应但本目录可包含更多解释与示例。

**受众**：所有开发者。

### 3.5 `decisions/` — 架构决策记录（ADR）

**回答**：为什么做了这个技术决策？考虑过哪些方案？

**内容**：
- ADR（Architecture Decision Records）
- 每条决策记录：背景、方案、取舍、结论、影响

**归属判断**：文档记录"一个重要决策的推理过程" → 放这里。

**命名规范**：`ADR-NNNN-简短标题.md`（如 `ADR-0001-dataset-backend-proxy.md`）。

**模板**：见 `decisions/_template.md`。

**对开发的价值**：开发遇到"为什么这样写"的疑问时，在这里找答案；做新决策时参考既有决策避免冲突。

**受众**：未来需要理解决策背景的人（包括自己）。

### 3.6 `analysis/` — 分析文档

**回答**：现状如何？有什么缺口？调研结论是什么？

**内容**：
- 缺口分析（如蓝图画布集成缺口）
- 技术调研（如开源项目对比）
- 性能分析
- 现状审计

**归属判断**：文档是"对现状的分析与调研结论" → 放这里。

**生命周期**：分析文档的结论若转化为正式设计，应沉淀到 `specs/` 或 `architecture/`；本目录保留原文作为历史记录。

**对开发的价值**：开发理解"为什么有这个缺口/为什么要改"的背景，是 specs 的前置输入。

**受众**：开发、产品（决策依据）。

### 3.7 `plans/` — 执行计划

**回答**：某个改进或功能怎么落地？分几步？**当前进度如何？**

**内容**：
- 执行计划（如画布拖拽优化计划）
- 迁移计划
- 重构计划
- 任务分解与进度跟踪

**归属判断**：文档是"有时间线、有步骤、有进度跟踪的落地计划" → 放这里。

**生命周期**：**临时性**。计划完成后，文档归档到 `plans/archive/`，结论沉淀到 `specs/` 或 `architecture/`。

**对开发的价值**：开发执行任务时的进度看板与步骤指引。计划完成后，长期可复用的部分必须沉淀到 specs/conventions，避免知识丢失。

**受众**：执行者、进度跟踪者。

## 4. 文档元信息约定

每个文档顶部必须包含：

```markdown
# 文档标题

> 状态：<草稿 | 设计中 | 评审中 | 生效中 | 已归档>
> 最近更新：YYYY-MM-DD
> 定位：一句话说明本文档的职责
```

- **状态流转**：草稿 → 设计中 → 评审中 → 生效中 →（变更后回到 设计中）→ 已归档
- **最近更新**：每次实质性修改后更新日期
- **定位**：帮助读者快速判断是否找对了文档

## 5. 文档命名规范

- 目录名：`kebab-case`（如 `dataset-management/`）
- 文件名：`kebab-case.md`（如 `data-model.md`）
- ADR 文件名：`ADR-NNNN-kebab-case.md`（如 `ADR-0001-dataset-backend-proxy.md`）
- 每个子目录必须有 `README.md` 作为索引

## 6. 索引维护

- **根 `README.md`**：列出所有层与重点文档，是文档入口
- **每层 `README.md`**：列出该层所有文档，含状态与简述
- 新增文档后，必须同步更新对应层的 `README.md`
- 文档状态变更后，同步更新索引中的状态字段

## 7. 文档与开发流程的关系

文档不是开发完成后的产物，而是贯穿开发全生命周期：

```
[product] 产品定义功能
    ↓
[analysis] 分析现状与缺口（如需要）
    ↓
[specs] 产出实现契约（Schema/API/UI/测试）
    ↓
[decisions] 记录关键决策（如需要）
    ↓
[plans] 分解任务、跟踪进度
    ↓
编码实现（遵循 conventions）
    ↓
[specs] 更新实现检查清单
    ↓
计划归档，结论沉淀到 architecture/conventions
```

**开发开始前**：specs 必须处于"生效中"或"设计中"（含明确契约）；conventions 必读。
**开发过程中**：plans 跟踪进度；决策变更写 ADR 或更新 specs。
**开发完成后**：更新 specs 的实现检查清单；plans 归档；可复用经验沉淀到 conventions 或 architecture。

## 9. 新增文档流程

1. 判断文档属于哪一层（参考第 3 节归属判断）
2. 在对应层目录下创建文件（遵循命名规范）
3. 文档顶部添加元信息（状态/最近更新/定位）
4. 更新该层 `README.md` 索引
5. 若是重要文档，更新根 `README.md`

## 10. 文档生命周期

```
[草稿] → [设计中] → [评审中] → [生效中] ─┬─→ [已归档]
                                          └─→ (变更) → [设计中] → ...
```

- **草稿**：刚创建，内容不完整
- **设计中**：正在撰写，内容逐步完善
- **评审中**：提交评审，等待反馈
- **生效中**：评审通过，作为正式依据（开发可据此实现）
- **已归档**：过期或被替代，保留历史

`plans/` 下的文档在计划完成后直接归档；`analysis/` 下的文档在结论沉淀后可保留或归档。

## 11. 双依据定位说明

本目录同时服务两类用途：

| 用途 | 核心层 | 文档特征 |
|---|---|---|
| **产品文档依据** | product / specs / analysis | 描述功能定义、边界、用户体验，产品可据此验收 |
| **开发实现依据** | architecture / specs / conventions / decisions | 描述系统结构、实现契约、编码规范，开发可据此实现 |

`specs/` 是两类用途的交汇点：既定义产品规格（产品验收依据），又包含实现契约（开发实现依据）。因此 specs 文档必须同时满足"产品可读"与"开发可执行"两个标准。
